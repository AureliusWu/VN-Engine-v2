# 多槽存档备份

`mountGame().continuation.latest()` 在独立会话校验后选择时间最新的有效 Auto / Quick / Manual 槽；相同时间优先 Auto、Quick，再按手动槽顺序。`resume()` 在点击时重新读取并恢复，损坏 / 不可达的候选原字节保留，不影响其他有效槽。首次挂载保留已有 Auto（包括损坏或暂时不可读的槽位），直到玩家进行实际翻页、动作、读档或新游戏；空 Auto 才初始化开场存档。

适用版本：0.3.0 alpha。玩家在设置页选择“备份所有存档”，导出当前游戏已用的手动、快速和自动存档。“导出存档 / 导入存档”继续处理单个当前位置，与整体备份分开。

“恢复存档备份”先读取并验证整个文件，再预览备份时间、槽位、保存时间、标题以及将覆盖的内容。只有“确认恢复这些槽位”写入。取消不写存档。成功后当前位置不跳转，玩家通过读档面板选择继续；未列出的槽位不会删除。

## 格式与验证

文件使用 `format: VN_ENGINE_SAVE_BACKUP`、`version: 1`、`game`、`createdAt` 和 `slots`（SaveEnvelope v2 数组）。每个 envelope 保留各自 save_version / game_version / slot / savedAt / payload / summary。只接受配置的手动槽、quick、auto；大小限制为 16,000,000 个 UTF-8 字节，单个 envelope 继续使用原存档限制。

`createSaveBackup(contract, storage, validatePayload)` 提供 `export()`、`preview(raw)`、`commit(preview)`。宿主必须注入独立的路线验证器。`mountGame().backup` 已接入真正的独立 RuntimeSession，按挂载时的项目副本恢复路线、变量与小游戏日志后重新生成 payload；作者后续修改输入对象不会改变验证基准。不在当前会话里试读，不创建媒体或存储订阅。四种叙事驱动都通过该边界验证。包内摘要只是显示信息，不能成为路线或解锁的权威。

备份头 / envelope / payload 的身份和版本必须兼容。跨游戏、不支持的版本、重复 / 越界槽位、无效路线或伪造小游戏结果会在任何写入之前被拒绝。核心 API 可使用契约中明确注册的迁移；默认 mountGame 不自动接受其他故事版本。

导出只枚举显式的游戏槽位，不枚举整个 storage。损坏或不可用的已用槽位会使导出失败并保留原始字节，避免产生悄悄缺少某个槽位的备份。普通存档之外的 Meta 收藏、设置、独立已读集合和其他游戏数据不纳入备份，不会隐式重置或解锁。

## 冲突与失败

预览对象不可变、仅对创建它的 backup 实例有效，并且只能提交一次。引擎记录预览时每个目标槽位的原字节，在确认时复核；发生变化返回 `conflict`，不写任何槽位，玩家需要重新预览。`StoragePort` 没有跨标签页事务能力，这只是确认前的冲突检查，不保证并发写入的全程原子性。

通过冲突检查后使用已有 `writeBatch`：配额 / I/O 失败时尝试恢复已经写入的槽位。返回 `rollbackFailed:false` 表示恢复操作没有报错；`true` 明确提示部分槽位可能未还原，不宣称原数据完全保留。玩家应保留备份再检查槽位。关闭或更换导入面板后，迟到的文件读取不会执行恢复。

浏览器测试实际下载 JSON、上传文件、预览 / 取消 / 确认、检测冲突并读取恢复的槽位；Windows WebView2 smoke 通过程序设置文件输入运行相同流程，不冒充人工操作系统文件选择器。
